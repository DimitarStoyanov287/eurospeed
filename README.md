# EUROSPEED · Junior ERP Assessment

Eurospeed test exam repo, designed for future candidates.

Интерфейсът е подготвен за GitHub Pages. Реалните покани, отговори, таймери и имейли използват съществуващия backend. Публичното репо не съдържа еталонните решения, администраторски ключове или реални кандидатски данни.

## Публикуване на интерфейса

В GitHub → Settings → Pages избери **Source: GitHub Actions**. Workflow `Publish candidate site to GitHub Pages` изгражда кандидатския и администраторския интерфейс от `main`. Тази еднократна настройка изисква достъп до настройките на хранилището.

За локален build: `pnpm install --frozen-lockfile`, после `pnpm build:github`. Получава се `github-dist/` с `index.html` и `admin.html`. PGlite файловете се копират от фиксираната npm зависимост при build; не са нужни бинарни файлове в Git.

Оригиналният backend е на `https://eurospeed-junior-test.eurospeed-4437.chatgpt.site`. Той позволява cross-origin API заявки само от изрично зададения GitHub Pages origin, а достъпът до отговори и администрация продължава да изисква индивидуален токен или администраторски ключ.

Администраторският панел генерира индивидуални кандидатски линкове за адреса, от който е отворен. Общият адрес на сайта показва информация и демо; за реален тест кандидатът трябва да получи индивидуална покана.

---


Практически тест за junior ERP разработчик: PostgreSQL, JavaScript и обяснение. Интерфейсът е на български. 50 минути, индивидуални покани, сървърен краен срок, запазване, история на редакциите и ръчна оценка. Кодът използва Vinext/React, Cloudflare Workers и D1; видимите SQL примери се изпълняват с PGlite в отделен браузърен Worker.

## Работа локално

Node.js 24 и pnpm 11.25.0 (зададен в `packageManager`).

```sh
pnpm install --frozen-lockfile
pnpm test
pnpm exec tsc --noEmit
pnpm build
pnpm dev
```

За сървърните операции са нужни D1 и `ADMIN_KEY`. Локалните секрети се задават в `.dev.vars`, който се игнорира от Git. След build приложи всяка SQL миграция от `drizzle/` към локалната D1 чрез Wrangler. Пример:

```sh
pnpm exec wrangler d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0000_pale_johnny_blaze.sql
pnpm exec wrangler d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0001_big_the_captain.sql
```

Тестовете използват локална SQLite и симулирана пощенска услуга. Не изпращат реални писма. Браузърното изпълнение на примери не е автоматична оценка и не се приема за доказателство за знания или за употреба на AI.

## След предаване

Само успешно натискане на „Предай“ създава две независими писма в същата D1 транзакция, която заключва отговорите:

1. Известие до `d.stoyanov@eu-speed.com` с кандидат, дата и адрес на панела, без администраторски ключ.
2. Благодарствено потвърждение до имейла, зададен при създаване на поканата.

Получателите и съдържанието се определят от сървъра. Кандидатът не може да подава произволен получател или текст. И двете писма се изпращат от Google акаунта `d.stoyanov@eu-speed.com`. Не се разпращат стари предадени решения със задна дата. Изтичането на таймера заключва последния запис, но само по себе си не създава писма.

Устойчивата опашка има отделен ключ за всяко писмо, заключване при обработка и повторни опити с изчакване. Google скриптът пази маркери за изпратените писма. При неясен резултат изпращането не се повтаря автоматично; прегледай „Изпратени“ в Gmail. „Изпратено“ означава прието за изпращане от Google, а не потвърдена доставка до входящата поща.

## Еднократно настройване на изпращането

В администраторския панел отвори **Настрой изпращането**. Там има готов скрипт, ключ за свързване и поле за адреса на услугата.

1. С акаунта `d.stoyanov@eu-speed.com` създай проект в Google Apps Script.
2. Постави `integrations/google-apps-script/Code.gs`. Manifest файлът е предоставен до него за минимални send-mail и userinfo.email права.
3. В Project Settings → Script Properties задай `MAIL_WEBHOOK_SECRET` с ключа от панела.
4. Deploy → New deployment → Web app: **Execute as Me**, **Who has access: Anyone**. Разреши изпращането от своя акаунт. Workspace политиката трябва да позволява този тип deployment.
5. Постави върнатия `/exec` URL в настройката на панела.

Скриптът проверява HMAC подпис, време на заявката, получателите, реалния изпращащ акаунт и предишно изпращане. Не разчита на публичността на URL като защита. Ключът е само сървърен и не е част от репото.

При текущото Sites публикуване опашката се задейства след ново предаване; неуспешните писма могат да бъдат обработени от панела. При самостоятелното Cloudflare публикуване GitHub workflow задава и Cron на всеки 5 минути за повторни опити.

## GitHub и самостоятелно публикуване

При самостоятелно преместване на backend-а еталоните трябва да се добавят само в защитената сървърна конфигурация. Публичното копие на `lib/rubric.ts` е placeholder. GitHub Pages не изпълнява този backend. Подготвени са CI проверки и GitHub Actions → Cloudflare Workers + D1.

Преди първо самостоятелно публикуване създай Cloudflare D1 database и задай в GitHub repository:

| Вид | Име | Стойност |
|---|---|---|
| Secret | `CLOUDFLARE_API_TOKEN` | Token с необходимите Workers deployment и D1 права за твоя account |
| Secret | `CLOUDFLARE_ACCOUNT_ID` | Cloudflare account ID |
| Secret | `ADMIN_KEY` | Силен ключ за твоя администраторски панел |
| Secret | `MAIL_WEBHOOK_SECRET` | Същият ключ като в Google Apps Script |
| Variable | `CLOUDFLARE_D1_DATABASE_ID` | UUID на новата D1 база |
| Variable | `CLOUDFLARE_WORKER_NAME` | Например `eurospeed-assessment` |
| Variable | `SITE_BASE_URL` | Финалният HTTPS origin на сайта |

Настрой **production environment** в GitHub; ако добавяш variables на environment ниво, задай също трите non-secret variables на repository ниво, защото те определят дали deploy job започва. GitHub deployment workflow не започва, докато трите variables не са зададени. Ново качване в `main` пуска тестове, build, schema миграции и deployment. Миграциите са append-only. Secrets се подават през временен файл само на GitHub runner-а и се изтриват след deployment; не се commit-ват и не се качват като artifact.

`scripts/prepare-external-deploy.mjs` създава отделна конфигурация в `dist/server/wrangler.external.json`. Запазва оригиналната Sites идентичност и не променя текущата публикувана база.

**Съществуващи кандидати:** самостоятелната Cloudflare база е нова и празна. Текущите покани, решения и настройки не се прехвърлят чрез Git. Преди смяна на активния адрес трябва да се направи отделен проверен пренос на данните, ако има реални кандидати. Препоръчително е първото публикуване да се провери с нов тестов кандидат. Администраторският ключ никога не се добавя към линковете за кандидатите.

## Структура

- `app/api/assessment/route.ts`: покани, срокове, отговори, оценки и настройка на пощата.
- `lib/mail.ts`: фиксирани получатели, шаблони, подписване и обработка на опашката.
- `integrations/google-apps-script/`: услуга за изпращане от твоя Google акаунт.
- `worker/index.ts`: следзаявкова обработка и самостоятелен Cron.
- `drizzle/`: versioned schema миграции.
- `.github/workflows/`: проверки и публикуване.

Браузърните сигнали не доказват измама. Блокирането на копиране на условието е само допълнителна пречка. Кратката защита на собствения код остава част от оценяването.
